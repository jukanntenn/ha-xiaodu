# RFC: 双语文档配对与配对门禁

Status: implemented

[English](2026-09-07-bilingual-pairing-gate.md) | 中文

## 问题

本仓库的文档同时被英文和中文的读者与 agent 阅读。没有任何机制、纯靠手工维护第二种语言，正是翻译腐烂的方式：一侧向前走，另一侧悄悄地说谎，没有门禁会注意到。任何机械化的答案都会引出三个更窄的问题。双语文档对会引用其他文档，若两侧使用完全相同的链接路径，中文读者会在文档中途被弹到英文页面；若两侧任意链接，结构比较就无法把两侧的链接视为"同一个链接"。文档对的一致性记录在每个编辑该对的分支上都会变化，两条这样的分支合并时，Git 会把两份 hash 记录按文本合并成垃圾——记录指向从未同时存在过的 blob——门禁随后报告的"漂移"其实只是合并产物。而对侧更新本身也有一个诱人却错误的默认做法：整篇重译会丢弃已评审的措辞并让既定术语漂移，而为一处两行的编辑加载整套指南语料，恰恰是在向契约所希望的行为——在同一个 PR 里把对侧一并带上——征税。

## 决策

### 权威对等的成对同名文件

一个文档对是三个同名文件：英文 `foo.md`、中文 `foo.zh.md`，以及一致性记录 `foo.i18n.yaml`。两种语言都不是规范来源——一篇文档可以先以中文撰写和评审、之后再翻译成英文，反之亦可；把这一对绑在一起的是两侧必须说同样的话，且文档对整体合并（两种语言加记录，绝不单独一侧）。归属的契约是 [i18n README](../../../../docs/i18n/README.zh.md)。

`foo.i18n.yaml` 保存两侧在最后一次确认一致时的完整 git blob hash。于是任一侧未经重新确认的编辑都能作为纯内容比较被机械检出——无需查历史——而且同一 PR 内编辑的文件也能算出 hash，这是commit hash 记录做不到的。重录（`hdsh pairing record <pair>`，要求点名已确认的文档对；批量重录是显式的 `--all`）会产生一份可评审的 yaml 差异，因此确认一致是 PR 中一个显式、可见的动作。录制会先把两侧快照存入本地对象库，并把每个存储的 blob 钉在 `refs/hdsh/pairing/snapshots/` 下一个按内容寻址的引用上，因此已记录的恢复指针能挺过垃圾回收，连从未提交的 worktree 字节也保持可恢复。

### 门禁

`hdsh pairing verify`（钩子 id `hdsh-pairing-verify`）强制：每个被发现且未排除的源文件都有完整的配对；每个既有配对都完整且一致（两侧 hash 匹配、中文侧和所有撰写的英文源都带语言切换行、结构签名相同）；被排除的文件不带 `.zh.md` 也不带记录。结构签名比较按顺序的标题层级、逐字节相同的围栏代码块、表格行列数、列表类型、有序列表起始值与项数，以及每个链接的语义目标及其精确的 query 或 fragment 后缀；切换行被排除，因为其语法恰好只允许一个链接；生成区块在两侧的配对文档 locale 路径归一化为配对锚点之后再比较。manifest `.hdsh/pairing.manifest.json` 只包含显式排除项、豁免英侧切换行的 `generated` 生成英文源数组，以及接受绝对形态切换行的可选 `public_blob_root` URL 前缀，因此没有任何要求能绕过发现而接受更弱的检查。

范围是每个 README（大小写不敏感的基名）加 `docs/**` 与 `.agents/rfcs/**`，依赖、虚拟环境和构建输出树以及冻结的 `.agents/rfcs/archived/` 树不在发现范围内；根级策略文档（按基名 `CONTRIBUTING`、`BRAND_GUIDELINES`、`SAFETY` 识别）即使位于文档目录之外也遵循同样的规则；本仓库当前没有这类文件。范围内的每篇文档自创建起就要求完整配对：没有按文件的推广状态、日期截止线或 README 专属类别。生成式英文源在 manifest 的 `generated` 数组中具名：它们配对但不带英侧切换行（生成器写出该行会使自己的新鲜度检查失败），其中文对侧仍链接回英文；本仓库目前该数组为空。

限定范围的调用服务于更新循环：以文档对路径点名的检查只触及这些文档对（文档对三个文件中的任一个或裸文件名都能点名），`--cached <pairs...>` 为钩子检查精确的暂存索引字节，`hdsh pairing list` 打印每篇文档的状态（missing、out-of-sync、ok）而从不失败。全语料形式仍是权威检查，在 CI 中运行。

### 本地化链接

每个普通的相对文档链接使用其所在侧的语言：英文侧链接到同级 `.md` 路径，中文侧链接到 `.zh.md` 路径，门禁会报告错误语言的目标并给出期望的 URL。语言切换行是唯一显式的跨语言例外；在 GitHub 之外渲染的 README 可以用 manifest `public_blob_root` 前缀配置的绝对 URL 指向其精确的对侧文件，使切换行在那里仍能解析。目标按语义比较：指向活跃双语语料的链接归一化为与语言无关的配对锚点及其精确的 query 或 fragment 后缀，因此同一目标的 `.md` 与 `.zh.md` 形式在结构签名中相等；语料之外的目标和外部 URL 保持原始字节并豁免。语料中缺失的对侧文件是配对完整性错误，绝不是静默回退。链接文本与其他散文一样翻译。

### 记录在合并时以 fail-closed 的方式组合

`.gitattributes` 把 `*.i18n.yaml` 路由到 `hdsh-pairing` 合并驱动，该驱动由 `hdsh worktree install` 以 `uv run --no-sync hdsh pairing merge-driver %O %A %B %P` 按 worktree 本地注册，这个 CLI 入口吸收了原先的 shell 启动器。驱动读取祖先、当前和对方记录，从 Git 对象库加载每份记录所记的两个所属 blob，并核对每个 blob 的内容与其记录的 hash。它对英文与中文所属文件各自独立运行 Git 默认的文本合并；若任一侧存在内容冲突，或合并后的文档丢失必需的切换行、违反链接语言或结构分歧，驱动即失败并保留普通冲突。成功时它把合并后的所属文件存为 blob、钉在快照引用命名空间下、写出组合后的记录并以 0 退出，Git 据此解析该路径。组合失败时，该入口在记录文件里写入普通文本冲突，打印恢复指引，并以非零退出让 Git 保持索引阶段未解析；运行时本身未同步时驱动命令直接失败，Git 以驱动错误停止合并（`--probe` 报告可用性）。未经核实的干净文本合并绝不算作已解析的配对记录。

`hdsh pairing merge --resolve` 在合并已经停下之后执行同样的 fail-closed 操作：它解析每个可机械组合的侧车冲突，把记录作为一批暂存，证明暂存的所属文件合并与组合结果一致且worktree 字节没有未暂存改动，拒绝覆盖已被编辑的冲突内容，并以失败退出并列出仍需手工处理的内容。

### 对侧更新是最小化的，并在编辑当轮完成

编辑任一侧都要求同一个 PR 把对侧一并带上，而这次更新是相对于对侧最后确认状态的最小差异——绝不是整篇重译，后者会丢弃已评审的措辞、让既定术语漂移，代价也最高。例行翻译由当前 agent 一次完成、一遍通过：加载[术语表](../../../../docs/i18n/terminology.md)，只翻译变更的内容，当真正的首次出现跨越编辑边界时移动术语首次出现标注，保留变更之外已评审的对侧散文，然后重录文档对。新文档对、整篇翻译和困难的对账是升级路径，由人显式选择而不是按变更大小推断。语义层面的翻译质量仍由人工评审负责。

## 行业先例

带语言后缀的成对同名文件是中国大厂仓库的主流惯例（ant-design 的 `index.zh-CN.md`/`index.en-US.md`、arco-design 带文首切换行的 `README.zh-CN.md`、Apache ShardingSphere 的 `.cn.md`/`.en.md` 文档对），但它们都不在 CI 中强制配对或一致性——惯例仅靠评审维持。一致性自动化存在于别处：MDN 的 `l10n.sourceCommit` front-matter 指纹、Vue 的 Ryu-Cho 上游提交监视器、Kubernetes 的本地化漂移脚本，以及 Microsoft 基于源 hash 驱动的 co-op-translator。本设计把两者结合——中文生态的文件布局加 hash 配对门禁——并把更新作为同一 PR 内的 agent 工作来完成，而不是一个 bot 服务。

## 备选方案

**以英文为规范来源并在译文内嵌指纹。** `.zh.md` 文件会携带记录英文源 blob hash的 HTML 注释，翻译单向流动。否决：中文优先撰写且权威对等无法用单向的规范模型表达；覆盖两侧的侧车保留了 blob hash机制而去掉了方向性。

**语言目录（`docs/en/` 加 `docs/zh/`）。** 否决：没有把语言映射到路由的文档站框架，移动每个英文文件会搅动每个交叉引用，链接检查也需要路径映射逻辑而不能原样工作。

**独立的翻译仓库。** 适合有独立发布节奏的文档产品，对治理仓库自身的文档而言过重，且把翻译置于本仓库门禁触及不到的地方。

**交错的双语文件。** 每个差异翻倍，破坏每段一行惯例的差异可读性，并让部分不一致不可见。

**commit hash 记录。** 同一 PR 内的编辑尚无 commit hash，这样的记录无法表达"截至本 PR 引入的状态为止一致"，核实它也需要 git 历史而非文件内容。

**比较文档对的 git 时间戳。** 仅格式的编辑会误报，在无关编辑之后提交的对侧文件会漏报；内容同一性是唯一名副其实的信号。

**两侧使用相同链接。** 每种语言的读者都会被扔进另一种语言的文档，且每个交叉引用看起来都相同而非本地化。

**在渲染时按读者选择语言。** 本仓库与 GitHub 的 Markdown 视图之间没有渲染步骤；链接是静态文本，语言必须烘焙进路径。

**在预处理阶段改写链接。** 源文件必须如所撰写般正确；修补步骤会让检入的字节与评审者阅读、门禁核实的内容不同。

**对记录用 union 或 theirs 合并。** 得到的记录会指向一侧的 blob 而树里放着合并后的文档；门禁随后会把每次双侧编辑都判为不同步。

**合并时从合并后的文档重新生成记录。** 生成的记录会悄悄确认一次驱动从未核实的合并；记录的含义是"有人确认了这些精确内容"，合并器无法授予。

**把记录存放在 Git 之外。** 记录必须与它描述的文档以同样的分支机制合并；旁路通道会失去原子性和历史。

**以整篇重译作为更新路径。** 保真度崩塌，因为已评审的措辞被丢弃、术语漂移，且是最昂贵的路径；最小更新规则成立。

**在侧车中按段落记录翻译记忆。** 段落边界在文档对两侧可能合理地不同，任一侧都可能先撰写，分段记录会膨胀并在合并中冲突；整文件 hash加按需比较能在可信时恢复对齐。

**为例行编辑自动调用翻译技能。** 另一个自动技能会在当前 agent 凭术语表和常设指令即可直接完成的任务周围增加发现上下文和调用边界，而按大小推断何时升级是隐藏政策。

## 影响

- 编辑配对文档的任一侧都要求同一 PR 更新对侧并重录文档对；承载该不变量的是 CI 而非评审者记忆，一处小编辑的成本与编辑本身成比例。
- 每个文档对为树增加第三个机器写出的文件；作为交换，"谁在何时确认了这两者一致"可从 yaml 的 git blame 回答，记录的 hash 兼作恢复指针，修复漂移的文档对是相对于被编辑侧的最小差异。
- 两侧不一致时，没有机械规则挑选赢家——由 PR 评审决定。这是权威对等的代价，经审慎接受，因为规范语言会禁止中文优先撰写。
- 只含排除项的 manifest 让当前和未来所有范围内的文档都经同一路径强制配对；新建语料内文档必须预先命名其配对，因为指向未配对文档的链接会让门禁失败而不是悄悄跨越语言。
- 只要对侧存在，跟随任何链接都会让读者留在自己的语言中；语料范围变化时，语料谓词、链接解析和结构签名必须一起变动。
- 只要文档本身能干净合并，同一文档对的两分支并行编辑就无需手工处理侧车；任何疑虑——运行时不可用、所属文件冲突、结构分歧——都留下普通 Git 冲突，恢复路径与无驱动合并相同，且组合后的记录只与它所组合的文本合并同样可靠。
- 门禁通过意味着该对在当前内容上的一致性已被确认，而非确认本身正确：检查读取 hash和 Markdown 结构，无法判断两侧是否说了同样的话；准确性、术语和流畅度仍是评审责任。
