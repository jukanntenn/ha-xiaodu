# RFC: 本地 Git 工作流：窄钩子、worktree 本地安装、审慎的分支历史与出站证据

Status: implemented

[English](2026-09-07-local-git-workflow.md) | 中文

## 问题

本仓库的工作在同一个克隆的多个关联 worktree 中进行，且主要由 coding agent 完成，本地 Git 工作流的每个环节都有一个"显而易见却是错的"默认做法。贡献者能想到的每个门禁都是 pre-commit 钩子的候选，但每加一个都会向每个 worktree 的每次提交征税；完整门禁矩阵（ruff、basedpyright、ty、100% 分支覆盖率要求下的 pytest、全语料配对检查）耗时足以让贡献者开始绕过钩子，而这比少跑几个钩子更糟。Git 为每个仓库只保留一个共享的 hooks 目录，因此仓库级 `core.hooksPath` 会让修改了 `prek.toml` 的分支改变其他所有 worktree 的钩子行为、让两个安装器互相竞争、让写入 `.git/hooks` 的 `prek install` 悄无声息地只覆盖主 worktree。并发运行互相独立的门禁是缩短等待时间的显然做法，但自研并行执行器必须自己负责进程管理、输出交错、取消和失败聚合，而这些 prek 已经提供。PR 的基线可能在当前尖端正被合入分支时继续前进：从更新的尖端重来会丢弃已完成的冲突解决和验证，重写已推送的合并则抹掉可评审的历史。最后，推送前检查、代码评审和文档审计都需要相对于真实基线的差异，但 `origin/<当前分支>` 在新 worktree 分支首次推送前并不存在，对 PR 目标为另一特性分支的堆叠分支也会误判；错误的范围会悄悄漏掉受影响路径，而三点式的已提交差异对暂存、未暂存和未跟踪三层一无所知。

## 决策

本地工作流是一套包含五部分的政策：钩子保持窄、钩子按 worktree 安装、prek 拥有并发、分支历史审慎选择、出站变更由显式报告度量。

### 本地钩子是快速的、以暂存面为界的检查点

[`prek.toml`](../../../../prek.toml) 安装 `pre-commit`、`pre-merge-commit` 和 `pre-push` 钩子，它们在 uv 管理的环境内运行（`uv run --no-sync …`），因此 prek 不构建独立的钩子环境。pre-commit 只运行成本受暂存面约束的检查：prek 内建的空白修复器（排除配对记录和冻结的 `.agents/rfcs/archived/` 树，二者的字节必须保持稳定）、暂存配对记录检查（对暂存的 `*.i18n.yaml` 运行 `hdsh pairing verify --cached`）、暂存的 `ruff check --fix` 与 `ruff format`、`git diff --cached --check`、RFC 格式门禁（`hdsh rfc verify`）与冻结归档门禁（`hdsh rfc archive`），以及在 Markdown 或 docs manifest 被暂存时运行的三个文档语料门禁（`hdsh docs wrap`、`hdsh docs links`、`hdsh docs budgets`）。pre-push 对整棵树运行 `basedpyright`。会重写文件的修复类钩子以非零退出，调用者需重新暂存并再次提交。

其余一切归 CI：带 100% 分支覆盖率门禁的完整 pytest、全语料配对检查、`ty` 和平台矩阵。局部的绿永远不能替代 CI 的穷举运行；新增一个钩子必须论证它是快速的暂存面检查点，而不仅仅是有用。

### 钩子按 worktree 本地安装

`hdsh worktree install`把钩子安装到 worktree 私有的 git 目录，而不是共享目录：

- hooks 目录是 `<worktree-git-dir>/hdsh-hooks`，由记录版本、所有者和绝对路径的所有权标记（`.hdsh-hooks-owned`）守护。安装器拒绝创建、使用或覆盖任何不是它自己拥有的常规目录的 hooks 目录，并拒绝目录内多重链接或非常规的条目。
- 按 worktree 配置要求 `extensions.worktreeConfig` 加仓库格式 1。安装器先校验公共配置——拒绝休眠的扩展、`core.worktree` 和 `core.bare=true`——然后再迁移。
- `core.hooksPath` 和 `merge.hdsh-pairing` 合并驱动配置只写为 worktree 作用域配置。安装器拒绝遮蔽继承值或替换 worktree 作用域的自定义值；`HDSH_PREK_ALLOW_HOOKS_PATH_OVERRIDE=1` 是针对用户自有继承路径的显式例外。命令作用域的配置永不被替换。
- 安装由公共 git 目录中的 `hdsh-hooks-install.lock` 串行化，带基于 PID 的过期锁检测和大声失败的手动恢复错误。后续步骤失败时，所有自有配置写入都会回滚；`prek install --overwrite` 在环境中清除命令作用域 `GIT_CONFIG_*` 后运行。
- prek 原生支持仓库本地和 worktree 本地的 `core.hooksPath`，其 shim 无需额外胶水即可落到 worktree 本地目录。

### prek 拥有并行；门禁保持无副作用

每个门禁都保证并发执行天然安全：门禁读取暂存面或 worktree 面，至多写自己的输出（ruff 修复器只重写自己的暂存输入），不持有跨门禁的锁。安装器的锁只串行化钩子安装，从不串行化门禁执行。无法遵守这一契约的门禁在 `prek.toml` 中声明 `require_serial`——整树 `basedpyright` pre-push 钩子正是如此。

### 分支历史审慎选择

merge-forward 和 rebase 都是独立 PR 与堆叠 PR 允许的刷新历史，评审后亦然。[GitHub 工作流](2026-09-07-github-workflow.zh.md)拥有 stack 如何表示与落地，[堆叠 PR 落地技能](../../../skills/merging-stacked-prs/SKILL.md)在根 `AGENTS.md` 之下在两种历史间做选择。

选择 merge-forward 时，每个观察到的基线尖端都获得自己的合并检查点。若工作期间基线前进，先完成并验证正在进行的合并、提交它，并在任务授权推送时推送它；之后再拉取并在单独的合并提交中合入更新的基线。该 merge-forward 序列内的检查点永不放弃或重写。

选择 rebase 时，远程历史重写使用精确租约（`--force-with-lease=<branch>:<expected>`）或有租约保护的 `gh stack` 推送路径，远程已移动则中止；裸 `--force` 被禁止。相关检查在发布前运行；`gh stack sync` 是唯一例外，因为它把拉取、级联 rebase 和推送作为一个操作完成，所以每个被重写的层都在其后立即验证，在该证据通过之前受影响的 PR 一律不合并。

### 出站变更是一份显式的范围报告

`hdsh scope`要求 `--base <ref>`，接受默认为 `HEAD` 的 `--head <ref>`，并输出一份带版本的 JSON 报告。它把两个输入解析为提交并检测歧义，渲染前要求恰有一个合并基。报告记录不规范化合法路径空白的仓库根、输入引用、解析后的基线、头和合并基提交 ID，以及排序后的已提交、暂存、未暂存和未跟踪路径集。路径记录按原始 NUL 字节切分并以严格 UTF-8 解码；无效值会中止报告，而不是替换字符或把不同值折叠为一个。

已提交路径比较解析后的合并基与解析后的头；脏路径集始终描述当前 worktree 和索引，即使 `--head` 指向另一个提交。每次 Git 探测都禁用已配置的文件系统监视器和可选的加锁；diff 配置无法隐藏子模块或调用外部 diff 与文本转换驱动，重命名检测被禁用，因此重命名的两侧都保持可见。

该命令从不猜测或拉取基线、查询托管平台或选择测试。每个调用方工作流——[推送前检查技能](../../../skills/pushing/SKILL.md)、代码评审、文档审计——自行核实当前远程或 stack 状态、显式提供基线，并把这份事实报告作为证据选择或语义评审的输入。

## 验证

`tests/worktree/` 下的临时仓库测试钉住安装器的所有权标记、配置校验与作用域及安装契约；`tests/scope/` 钉住显式与堆叠引用、每一个脏层、合法路径空白、严格路径解码、无副作用探测、无效引用、确定性 schema，以及报告后引用、索引、配置与状态保持不变；pytest 在 100% 分支覆盖率门禁下运行。钩子集本身是像代码一样被评审的配置，`prek.toml` 始终小到一屏可读。

## 备选方案

**在 pre-commit 运行完整测试套件。** 提交延迟会增长一个数量级；贡献者会绕过或跳过钩子，连快速检查点也一并失去。

**在 pre-commit 运行全语料配对扫描。** 配对记录在暂存时已按字节精确检查；全语料发现和结构检查对大多数提交没有变化，属于 CI。

**完全不用本地钩子。** 暂存配对记录检查和空白卫生恰好捕获那些在暂存时最便宜修复、在 CI 里最恼人诊断的破坏类别。

**仓库外的共享 hooks 目录。** 所有 worktree 共用一个变更面，安装目标又在仓库所有权边界之外；卸载或升级一个 worktree 会悄悄改变其他 worktree。

**`.git/config` 中的仓库全局 `core.hooksPath`。** 同样的共享问题，只是存储在仓库内；关联 worktree 仍会继承主 worktree 的钩子状态。

**Git 默认的按 worktree `.git/hooks`。** 关联 worktree 确实有私有 git 目录，但没有任何机制让 prek 的 shim 在那里与 `prek.toml` 保持同步，而所有权标记正是卸载器安全的保障。

**仓库自有的并行门禁执行器。** 它会重复 prek 的进程池、输出解复用和取消语义，且每个钩子作者都得理解它们。

**为确定性串行化所有门禁。** 每个钩子内部的输出顺序是确定的；跨钩子交错只是表面问题，而串行执行会让每次推送的墙钟时间成倍增加。

**一个运行所有门禁的聚合脚本。** 单一进程在结束前隐藏了哪个门禁失败，破坏了快速失败，也无法通过 prek 单独选择或跳过。

**中止 merge-forward 并从最新基线重来。** 这会丢弃已解决的冲突和已完成的验证、重复劳动，并移除一个有用的恢复点。

**把两个基线尖端折叠成一个重写的合并。** 这隐藏了冲突解决的顺序，且若第一次合并已推送则需要重写远程历史。

**彻底禁止重写已评审的分支。** 一刀切的禁令也会把原生 `gh stack sync` 工作流排除在外——它的级联 rebase 带租约保护地更新每一层——并让独立 PR 与堆叠 PR 处于不同的历史政策之下。

**要求每次刷新都 rebase。** 线性历史有用，但当保留已完成的冲突解决及其恢复点比紧凑历史更重要时，合并检查点仍是合理选择。

**用临时 diff 命令加散文兜底来确定范围。** 这避免了一个仓库工具，却让普通的新 worktree 和堆叠基线拓扑在各工作流间不一致，还遗漏了脏层。

**从配置的上游推断基线。** 上游可能是首次推送前的 `origin/main`、推送后的同名特性分支，或 PR 目标为另一特性分支的头分支；没有哪种推断对所有拓扑都正确。

**在 scope 命令内部向 GitHub 查询基线。** 这把一个本地只读报告耦合到单一托管平台和网络凭据，却仍无法解析没有 PR 的分支。

**从变更路径生成所需测试。** 路径无法确立经由配置、动态加载、子进程或 worker 抵达的行为；证据选择仍是推送前检查下的判断。

**报告当前分支与上游并维护一个并行的人类可读渲染器。** 调用方在调用前已核实分支与基线状态，没有消费者使用这些字段，而格式化散文只是重复 JSON schema 且不改善路径完整性。

## 影响

- 提交保持快速，钩子集一屏可读；CI 拥有穷举门禁矩阵，因此本地钩子的绿从不构成整体健康的证据。
- 每个 worktree 的钩子与它自己的 `prek.toml` 一致；在一个 worktree 切换分支从不影响另一个，删除 worktree 也会一并移除其钩子。安装器对任何无法核实的前提大声失败，保留先前的钩子状态；锁位于公共目录并在释放时移除。
- 门禁墙钟时间以最慢的单个门禁为界，而非总和；门禁独立性是代码评审要求，prek 升级可以在不改仓库的情况下改变调度行为。
- 基线反复前进时，一个 PR 可以携带多个基线合并提交；已完成的工作保持可评审、可恢复，合入更新的基线会改变合并后的树，因此下次推送前相关检查会再次运行。rebase 可能使commit hash、批准和评论锚点失效，因此每次重写推送都伴随一次实时的评审与检查重审计。
- 显式基线让错误的基线成为可能但可见：两个输入引用和全部三个解析后的提交 ID 都出现在报告中，调用方付出先核实并拉取实时基线的小额成本。字符串 schema 刻意无法表示非 UTF-8 的路径字节；含有此类路径的仓库必须先重命名它们才能生成报告。
